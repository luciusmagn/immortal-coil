#+TITLE: Immortal Coil Design Notes
#+DATE: 2026-06-08
#+LANGUAGE: en

This file is a current project note, not a speculative engine architecture.
The old HAMT/LMDB/patch-kernel plan was too large for the prototype and does
not describe the codebase anymore.

* Shape

Immortal Coil is a Common Lisp / Claylib narrative-game prototype.

The immediate goal is a small playable loop:

- stark black-and-white CRT text
- typewriter pacing and sound
- choices, inputs, branches, and text substitution
- minigames authored through the same dialog/mod surface
- particles and music controlled by dialog nodes
- hot-reload-friendly scripts and focused save data

"Dialogue tree" is useful industry language, but the runtime is allowed to be a
graph. Shared nodes, conditions, mod extension points, and genre branches all
benefit from graph behavior.

The bundled game is treated as the first dogfood mod. It loads through
=game/manifest.lisp= and uses the same public script forms that player mods use.

* Non-Goals For Now

Do not add these until the playable loop proves a concrete need:

- LMDB
- HAMTs
- persistent graph databases
- immutable patch kernels
- priority-bit patch systems
- sandboxed mod execution
- large storage architecture

Current defaults are plain Lisp data, script reloads, defensive runtime
warnings, and focused save data.

* Runtime Stack

#+begin_src text
main loop
  title/menu
  pause menu
  gameplay
    dialog node update/draw
    minigame update/draw
    particle field update/draw
    story music update

dialog/mod loader
  bundled manifest
  player mod manifests
  deterministic bundle order
  latest-wins node conflicts recorded for the menu
#+end_src

* Current Data Model

The dialog graph is an in-memory hash table of nodes. Nodes are not currently
persistent database records.

Node kinds:

- =:text=
- =:say=
- =:choice=
- =:number=
- =:string=
- =:minigame=
- =:branch=

Choices and branches can use conditions. Conditions may read the shared dialog
store or run explicit lambdas.

The shared dialog store is for author-facing facts:

- player name
- age or other input values
- inventory flags
- hidden branch flags
- minigame results

Dialog text and choice labels can substitute store values with ={store-key}=.

* Authoring Surface

Primitive node forms:

#+begin_src lisp
(dialog-start "base/awake")

(dialog-text "base/awake"
             "you awake in a strange world..."
             :next "base/feel")

(dialog-say "npc/greeting"
            "crewman"
            "captain {player-name}, we are ready."
            :next "ship/flight")

(dialog-choice "base/exit-bed"
               "exit bed?"
               (dialog-option "yes" "base/exited-bed")
               (dialog-option "no" "base/sleep"))

(dialog-pick "base/night-stand"
             "what do you take from the night stand?"
             (dialog-option "glass of water" "ship/wake")
             (dialog-option "matchbook" "jrpg/inn")
             (dialog-option "brass key" "forest/threshold"))

(dialog-list "rogue/door"
             "choose a door."
             (dialog-option "north" "rogue/north")
             (dialog-option "east" "rogue/east"))
#+end_src

Input nodes:

#+begin_src lisp
(dialog-string "ship/name"
               "what does the room call you?"
               :response-key "player-name"
               :target "ship/alarm")

(dialog-number "base/count-doors"
               "how many doors do you count?"
               :response-key "door-count"
               :min 0
               :max 9
               :target "base/door-count-branch")
#+end_src

Branches:

#+begin_src lisp
(dialog-branch "base/door-count-branch"
               (dialog-case '(>= (dialog-value "door-count" 0) 5)
                            "base/too-many-doors")
               (dialog-default "base/choose-door"))
#+end_src

Common path helpers:

#+begin_src lisp
(dialog-path "base/walk"
  "you find the hallway."
  "it finds you back."
  (:next "base/door"))

(dialog-pick-path "base/night-stand"
                  "what do you take?"
                  ("glass of water"
                   :id "glass"
                   "the glass is cold."
                   (:next "ship/wake"))
                  ("nothing"
                   "your hand returns empty."))
#+end_src

Development save override:

#+begin_src lisp
(dialog-dev-save-here
 :store '(("player-name" . "dev"))
 :visible :all)
#+end_src

* Effects

Node entry effects are plain Lisp forms evaluated when the node is entered.
They are intentionally unsandboxed during this prototype phase.

Current author-facing helpers:

#+begin_src lisp
(dialog-particles "ship/wake" :stars :fade-seconds 6.5)
(dialog-music "ship/wake" "audio/ship-lyria-drone.mp3" :volume 0.26)
(dialog-music "forest/threshold" "audio/forest-lyria-drone.mp3" :volume 0.28)
(dialog-stop-music "base/awake")
#+end_src

Particle fields currently include:

- =:rising=
- =:stars=
- =:title-menu=
- =:forest-wind=, defined by the bundled forest script

Scripts can define new particle fields:

#+begin_src lisp
(dialog-particle-field-kind :forest-wind
                            :reset #'reset-forest-wind-particles
                            :ensure #'ensure-forest-wind-particles
                            :update #'update-forest-wind-particles
                            :draw #'draw-forest-wind)
#+end_src

* Minigames

Minigames are registered through scripts and referenced by dialog nodes.

#+begin_src lisp
(dialog-minigame-kind :wire-flight
                      :update #'update-flight-minigame-node
                      :draw #'draw-flight-minigame)

(dialog-minigame "ship/flight"
                 "use w/a/s/d or arrow keys to steer. keep the ship inside the open wireframe gates."
                 :game :wire-flight
                 :success "ship/threaded"
                 :failure "ship/crash-return")
#+end_src

The runtime now has CLOS protocols under the function-backed DSL:

- =minigame-update=
- =minigame-draw=
- =particle-field-reset=
- =particle-field-ensure=
- =particle-field-update=
- =particle-field-draw=

That means future minigames and particle systems can become self-contained
objects when that removes real complexity. The author-facing scripts can still
register ordinary functions.

* Bundles And Mods

Bundled game manifest:

#+begin_src lisp
(:id "immortal-coil/base"
 :name "Immortal Coil"
 :version "0.0.1"
 :description "Bundled story graph."
 :depends-on ()
 :scripts ("maze/minigame.lisp"
           "maze/rendering.lisp"
           "flight/minigame.lisp"
           "flight/rendering.lisp"
           "opening.lisp"
           "campaign/forest.lisp"
           "campaign/jrpg.lisp"
           "campaign/dream-worlds.lisp")
 :assets "../assets/"
 :title-logo "logo/title-logo.png"
 :start "base/awake")
#+end_src

Player mod layout:

#+begin_src text
mods/<mod-id>/manifest.lisp
mods/<mod-id>/assets/
#+end_src

Minimal mod manifest:

#+begin_src lisp
(:id "example-mod"
 :name "Example Mod"
 :depends-on ("immortal-coil/base")
 :scripts ("story.lisp")
 :assets "assets/")
#+end_src

Total conversions can also set manifest metadata:

#+begin_src lisp
(:title-logo "logo/title-logo.png"
 :start "example-mod/start")
#+end_src

Bundle-local assets should be resolved with =dialog-asset-pathname= or helpers
that use it. Do not hardcode project-global paths in scripts.

Load order is deterministic:

- bundled game first
- mod bundles after it
- =:depends-on= can order one bundle after another
- remaining ties use path order
- latest loaded =:title-logo= and =:start= manifest metadata wins
- node conflicts are recorded and currently resolve as latest-wins

* Save Data

Saves are simple readable Lisp data. They currently store:

- version
- current node ID
- visible text count
- selected choice index
- input buffer
- dialog store
- particle field transition state

Default save path:

#+begin_src text
save/current.lisp
#+end_src

=IMMORTAL_COIL_SAVE_DIR= can override the save directory.

* Current Campaign Branches

Opening night-stand paths:

- glass of water -> hard-sci-fi ship captain loop and wire-flight minigame
- matchbook -> straight-faced JRPG branch
- brass key -> dark forest escape / hunted branch
- nothing -> door-count path into the dream maze

Dream maze exits:

- left -> Alice-style dream branch
- upper -> Rogue-inspired dungeon branch
- right -> returns toward the base room

Current draft branches are intentionally short. Their job is to prove the graph,
mod, minigame, music, and particle surfaces by using them in the bundled game.

* Narrative Direction

The core narrative tool is recontextualization. Future scenes add details,
names, surroundings, roles, and relationships that make earlier scenes mean
something different. The earlier scene should feel like it was always that
thing; the player simply lacked context.

Avoid transformation language:

- no objects changing into other objects because the player acted
- no corridors folding shut on cue
- no doors waiting to become something else
- no early explanation of loops or genre pivots

Ship captain path:

- the captain appears impeccable to the crew
- the player privately fails, dies, loops, and carries the pain forward
- crew praise should hurt because the player remembers the failed attempts
- hallucinations are memory intrusions from previous loops, not ghosts or omens

Forest path:

- begins as leaving a house in a black forest
- the player is hunted
- later reveal: the player had been kidnapped and unwittingly escaped
- the pursuer is the kidnapper, possibly supernatural
- do not reveal this early

JRPG path:

- initially reads as a plain inn / village / party / demon lord adventure
- later value comes from how the familiar frame recontextualizes the same room

Dream paths:

- one exit leads toward Alice-style dream logic
- one exit leads toward a Rogue-like dungeon frame

* Visual And Audio Direction

Visuals:

- pure black and white
- phosphor tint from CRT/bloom is acceptable
- no ordinary color palettes without a specific reason
- central text must stay readable
- particles are part of the fiction, not just decoration

Audio:

- alternating typewriter clicks for text
- substantial menu confirmation sounds
- beatless, long, drawn-out drone music
- no obvious drums, snares, bells, or rhythmic loop stitching

* Editor

The visual editor is served with:

#+begin_src sh
nix run .#editor
#+end_src

Open:

#+begin_src text
http://127.0.0.1:8080/tools/dialog-editor/
#+end_src

The editor should avoid forcing authors to write full Common Lisp into tiny
fields. Prefer templates and focused fields, with custom Lisp as an escape
hatch.

* Packaging

Nix is the reproducible build path:

#+begin_src sh
nix build .#immortal-coil
#+end_src

Linux binaries matter now. Windows packaging remains important for a future
Steam release, but should not derail the playable loop.

* Open Problems

- More story is needed before architecture work pays off.
- The built-in campaign should keep dogfooding mod surfaces.
- Mod conflict negotiation is only recorded/latest-wins right now.
- Story music is controlled by node entry effects but is not its own save field.
- Visual editor ergonomics still need more predefined templates.
- Windows packaging is still future work.
